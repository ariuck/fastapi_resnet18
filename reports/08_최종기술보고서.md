## 3. 아키텍처 및 데이터 흐름

- **동기:** Browser → FastAPI → Redis Cache(DB/1) → (MISS) ResNet18 → JSON
- **비동기:** Browser → FastAPI → `media/jobs` + PostgreSQL(queued) → Redis Broker(DB/2) → Celery Worker → Cache/ResNet18 → PostgreSQL(done) → 상태조회
- Docker에는 Redis·PostgreSQL만 있고, FastAPI·Worker는 WSL에서 실행된다. 모델은 두 프로세스에 각각 로드된다.
- 근거 문서: [산출물 2](02_시스템_아키텍처.md)

## 5. 실제 버튼 처리 검증

- **동기식:** 분류 완료 후 HTTP 200으로 결과가 함께 온다 (화면 `HTTP 200 / 응답까지 48ms`).
- **비동기식:** HTTP 202와 `job_id`를 먼저 받고, 1초 간격 폴링으로 `done`을 확인한다 (화면 `접수 35ms / 전체 1064ms / 상태 done`, job 14).
- Worker 로그에서 job 14가 0.083초 만에 처리된 것을 확인했다.
- 근거 문서: [산출물 5](05_AI버튼_처리흐름.md)

## 6. 실제 성능 비교 (중앙값, 워밍업 제외)

| 항목 | 값 |
|---|---:|
| Sync MISS HTTP 완료 | 20.0 ms |
| Sync HIT HTTP 완료 | 1.5 ms |
| Async MISS HTTP 접수 | 8.45 ms |
| Async MISS 최종 확인 (0.1초 폴링) | 115.55 ms |
| 모델 추론 (Sync / Async, CPU) | 14.78 / 20.58 ms |
| 모델 최초 로드 (FastAPI / Worker) | 약 5.5초 / 5.6초 |

- 비동기 접수 응답이 57.75% 빠르지만, **이는 접수와 처리를 분리한 효과이며 추론 가속은 아니다.** 최종 결과 확인은 비동기가 약 95ms 더 느리다.
- 동기 캐시 HIT는 HTTP 응답을 92.5% 줄였다(추론 생략).
- 근거 문서: [산출물 6](06_성능비교_보고서.md), 원본 [`data/timings.csv`](data/timings.csv)

### 6-1. 동기·비동기 방식 비교

| 비교 항목 | 동기 (`/api/sync/classify/`) | 비동기 (`/api/async/classify/` + 상태조회) |
|---|---|---|
| 응답 방식 | 요청 1번 → 추론이 끝날 때까지 대기 → 결과 포함 응답 | 요청 1번 → 즉시 접수 응답 → 결과는 상태조회 N번으로 확인 |
| 성공 상태코드 | 200 (= 완료) | 202 (= 접수일 뿐) → 상태조회 200 + `status: done` |
| 추론 실행 위치 | FastAPI 프로세스 | Celery Worker 프로세스 (별도) |
| 필요한 구성요소 | FastAPI, 모델 (Redis는 없어도 동작) | FastAPI, Redis 브로커, Celery Worker, PostgreSQL, 공유 파일(`media/jobs`) |
| 작업 기록 | 남지 않음 | `image_jobs`에 상태·결과·시간 기록 |
| 실측 HTTP 응답 (MISS 중앙값) | 20.0 ms | 8.45 ms (접수) |
| 실측 결과 확인 (MISS 중앙값) | 20.0 ms | 115.55 ms (0.1초 폴링) / 화면 1,064 ms (1초 폴링) |
| 모델 추론시간 | 14.78 ms | 20.58 ms (같은 모델, 같은 수준) |
| Redis 장애 시 | **200** — 캐시 없이 추론 계속 | **503** — 접수 불가, 행 `failed` |
| Worker 장애 시 | 영향 없음 | 202 후 `queued`로 대기, Worker 복구 시 처리 |
| 장점 | 구조가 단순, 결과를 바로 받음, 이번 측정에서 결과 확인이 더 빠름 | 긴 작업에도 HTTP 연결을 오래 붙잡지 않음, 작업 이력·재조회 가능, Worker 수를 늘려 처리량 확장 가능 |
| 단점 | 추론이 길어지면 요청이 그만큼 대기, 처리 이력 없음 | 구성요소가 많아 장애 지점 증가, 폴링 대기로 결과 확인은 더 늦음 |
| 적합한 상황 | 이번처럼 추론이 수십 ms로 짧은 단건 요청 | 대용량 이미지·배치 처리·추론이 수 초 이상 걸리는 작업, 처리 이력이 필요한 경우 |

**결론:** 이번 모델은 추론이 약 15~20ms로 짧아 **결과를 받는 시간은 동기가 더 빨랐다.** 비동기의 이점은 속도가 아니라 **접수와 처리의 분리, 작업 기록, 장애 시 대기열 보존**에 있다. 같은 이미지는 두 방식 모두 같은 결과(bean_rust 0.4638)를 냈고 Redis 캐시도 공유했다.

## 7. 기능 테스트·오류 조치

- 실환경 통합 테스트 T-01~T-11c PASS (Worker 정지 시 `queued` 유지 → 재실행 후 `done`, Redis 중지 시 동기 200·비동기 503 + `failed` → 복구 후 정상)
- 예외처리 12가지를 코드 위치·응답·기록 기준으로 정리 (X-1~X-12)
- Worker 추론 중 예외(`running → failed`)는 실환경 **미발생**, 모의 테스트로만 확인
- 실제 오류 이력: Python 3.11 부재(uv로 해결), ZIP 내 비이미지 파일(제외), Worker 워밍업 지연(측정 제외)
- 근거 문서: [산출물 7](07_기능테스트_오류분석.md)

## 8. 교과 9 OpenCV 기반 정확도 개선 실험 및 제안

> **구현·실측:** 학습량·Full Fine-tuning, CLAHE, 잎 마스크, 데이터 증강, OpenCV 특징 분류, CNN+규칙 보류 — **실행하고 같은 Validation으로 측정** (상세: [산출물 1](01_FineTuning_결과보고서.md) 7장)
> **미구현(제안만):** GrabCut 보정, Grad-CAM, CNN+ML 융합
> 모델 자체 성능과 후처리(보류 규칙)를 포함한 시스템 성능은 따로 보고한다.

### 8-2. 적용 방법과 결과

| 방법 | 처리 흐름 (교과 9 기법) | 상태 | Validation 결과 (비교 기준) | 판단 |
|---|---|---|---|---|
| 학습량·Full Fine-tuning | 제공 코드 옵션만 변경: epoch 10, `--freeze-backbone` 제거 + lr 5e-5 | **실행** | 3→10ep 0.7669→0.8947, Head→Full 0.8947→0.9699 | 가장 큰 개선 |
| CLAHE | BGR→LAB → L 채널 CLAHE(clip 2.0, 8×8) → 재학습 | **실행** | Head 0.8947→0.8872, Full 0.9699→0.9699 | 효과 없음 |
| 잎 ROI·마스크 | HSV `inRange`(H 22~100) → 타원 Opening/Closing → 면적 1.5% 이상 Contour 채우기 → 배경 제거 → 재학습. v1(사각 25×25 Closing)은 흙까지 메워져 v2로 조정 | **실행** (GrabCut 보정은 미구현) | Head 0.8947→**0.9398 (+6장)**, Full 0.9699→0.9549 (−2장) | Backbone 고정 시에만 효과 |
| 데이터 증강 | train에만 반전·90° 회전·밝기/대비 ±20% ×2 → 3,102장 | **실행** | Head 0.8947→0.9323, Full 0.9699→**0.9850** | 두 방식 모두 개선, **최종 선택** |
| HSV 병반 특징 분류 | 잎 마스크 안 갈색·황색 비율, 반점 개수·크기, HSV 통계 11개 → 로지스틱회귀 / 랜덤포레스트 (CNN 미사용) | **실행** | 0.6617 / **0.7744** | 기준선 CNN(0.7669)과 비슷, CNN보다 낮음 |
| CNN + 규칙 보류 | 1·2위 margin < 임계값이면 "확인 필요" | **실행 (분석만, API 미반영)** | E0: margin<0.2 → 보류 39%, 자동 판정 0.8642 / E7: 보류 1.5%, 효과 없음 | 약한 모델에만 의미 |
| Grad-CAM | ResNet 마지막 합성곱 특징맵 → 히트맵 → 잎·병반 영역과 비교 | 미구현 | — | 오류 분석용, 정확도 향상 수단 아님 |
| CNN + ML 융합 | CNN 점수 + OpenCV 특징 → 보조 분류기 | 미구현 | — | train 내부 교차검증으로 CNN 점수를 만들어야 누출이 없음 |

### 8-3. 최종 결과

| 모델 | Validation | Test (1회) |
|---|---:|---:|
| E0 기준선 | 0.7669 | 0.7188 (92/128) |
| E7 Full + 증강 | 0.9850 (2회 재현) | **0.9766 (125/128), +25.8%p** |

- 시연에서 틀린 `bean_rust_test.10`(→ angular 0.38), `bean_rust_test.30`(→ angular 0.44)이 E7에서 **bean_rust 0.95·0.98로 정답**

### 8-4. 설계 예시: OpenCV 병반 후보 검출 [특징 추출은 구현 · 단독 판정 규칙은 미구현]

```text
입력: 콩잎 JPG 1장
1. BGR → HSV 변환
2. 녹색 범위 inRange → 잎 후보 마스크 (Train 샘플로 범위 설정)

현재 상태: 1~5단계(잎 마스크·병반 비율·반점 특징)는 experiments/preprocess.py, opencv_features.py로 구현해
          특징 분류(R1·R2)에 사용. 면적비 임계값으로 병명을 판정하는 단독 규칙과 6단계 API 연동은 미구현
```
